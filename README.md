# Wheelchair Route Checker

This repo contains an indoor wheelchair route checker for IFC building models.

IFC is a building model file format. It stores things like doors, rooms, floors, stairs, ramps, and walls.

The app reads an IFC file, splits the building by floor, checks wheelchair routes between doors, and shows the result in a browser.

The final compliance decision is made by SHACL rules over RDF. Python prepares IFC geometry measurements and route geometry, but it does not create the pass or fail issue list.

The project also contains a prototype PDF-to-SHACL pipeline. It reads technical-standard PDF content, extracts canonical rules, requires approval before SHACL generation, generates SHACL deterministically, and then validates the IFC/RDF graph with pySHACL.

This is a working research prototype, not a production legal-compliance system.

## What The App Checks

The app checks these indoor wheelchair route rules:

- door or opening clear width must be at least 0.90 m
- main indoor route width should be at least 1.50 m
- turning space should be at least 1.50 m by 1.50 m
- stairs block a wheelchair route when the route path enters the stair area
- ramps must be at least 1.20 m wide and at most 6 percent slope

The app is only for indoor route checks. It does not check toilets, lifts, outdoor paths, fire safety, or full legal approval.

Stairs are shown separately from door-to-door routes:

- door and corridor routes stay green when their path does not enter the stair area
- stair approaches are shown as blocked because stairs are not wheelchair routes
- on upper floors and basement, the simulation starts from the stair landing before checking routes to doors

## How The Checker Works

The app uses these steps:

```text
IFC file
-> building elements and geometry
-> floor-by-floor route graph
-> RDF graph with IFC and route measurements
-> generated SHACL validation
-> website data
-> browser view
```

Rules can be prepared from a technical-standard PDF:

```text
PDF
-> Document Ingestion
   -> TextChunk
   -> ImageChunk
      -> embedded PDF images
      -> rendered full-page images
      -> rendered table-region images
   -> TableChunk
   -> PageMetadata
-> Requirement Extraction Agent
   -> reads text chunks
   -> reads OCR text from extracted PDF images
   -> reads vision-model observations from extracted PDF images
   -> detects canonical rule candidates
-> Canonical Rule Model
-> Human Review Workflow
   -> PendingRule
   -> ApprovedRule
   -> RejectedRule
-> Approved Rule Library
-> deterministic SHACL generator
-> pySHACL validation
```

The agent only creates canonical rule objects. It does not generate SHACL.
SHACL is generated by fixed Python templates.

The current extraction is reliable enough for a thesis demo on the supported wheelchair-route rule types, but it is not a general DIN 18040 rule extraction engine. The current generator supports these rule families:

- door clear width
- corridor or route clear width
- wheelchair turning space
- ramp slope
- ramp usable width

Current known limits:

- Agent purity is enforced. Deterministic repair logic may not create missing canonical rules.
- Rules do not become publishable without explicit review input through the preprocessing command.
- Vision processing uses ranked image selection. Embedded images, rendered full-page images, and rendered table-region images are scored, and the strongest chunks are sent to the vision model.
- The ontology mapping layer is deterministic and limited to the current accessibility vocabulary.
- SHACL generation is deterministic, but only for the supported rule families above.

The browser does not recalculate the IFC model. It only shows the data prepared by the Python scripts.

## Install

Install Python 3.12 first.

Then open a terminal in the repo folder and install the Python packages:

```powershell
python -m pip install -r requirements.txt
```

Optional tools:

- Ollama is needed for the local requirement extraction model and the local vision model.
- The tested text model is `qwen3.5:9b`.
- The tested vision model is `qwen3-vl:8b`.

Required tools:

- Java is required for IFCtoLBD.
- Maven is required to build IFCtoLBD from `IFCtoLBD-master.zip`.
- `IFCtoLBD-master.zip` must be present in the repo folder.
- pySHACL is required for validation.
- PaddleOCR is used for OCR over extracted and rendered PDF images.

The preprocessing step stops with an error if Java, Maven, IFCtoLBD, or pySHACL is not available. It does not create a Python replacement LBD graph.

The website checks Ollama when it starts. If Ollama is not running, start the website with `--yes` to continue and show SHACL report data instead of generated assistant text.

To prepare the tested local models:

```powershell
ollama pull qwen3.5:9b
ollama pull qwen3-vl:8b
```

## Run With The Included IFC File

From the repo folder, prepare the data from the included IFC file and the included DIN planning PDF:

```powershell
python preprocess.py --ifc ".\AC20-Institute-Var-2.ifc" --rules-pdf ".\planungsgrundlagen_barrierefreies_bauen.pdf" --save-bin --approve-rules --reviewer "your-name" --review-rationale "Reviewed extracted rules for this run"
```

Without `--approve-rules`, preprocessing stops after writing the extracted rule files. That is expected. It prevents SHACL publication without explicit review metadata.

The PDF pipeline uses a content-based cache under `output/app_package/_cache`. If the same PDF bytes, OCR provider, vision model, vision image budget, extraction model, and canonical rule schema are unchanged, preprocessing reuses:

- rendered PDF images
- OCR text
- vision observations
- structured document chunks
- extracted canonical rules
- extraction audit state

The cache status is written to `output/app_package/processing_cache_report.json`. Use `--no-cache` when you intentionally want a full fresh PDF extraction run.

Start the website:

```powershell
python server.py
```

Open this link in your browser:

```text
http://127.0.0.1:8765
```

If Ollama is not running and you still want to open the website:

```powershell
python server.py --yes
```

## Run With Your Own IFC File

Use the same command, but replace the file path:

```powershell
python preprocess.py --ifc "path\to\your\model.ifc" --save-bin
python server.py
```

Then open:

```text
http://127.0.0.1:8765
```

## Assistant Explanation

The assistant explains the checker result in normal language.

If Ollama is running with `qwen3:8b`, the app asks Ollama to write the answer.

If Ollama is not running, `python server.py` stops and prints a message. Use `python server.py --yes` to continue. In that mode, assistant requests return SHACL report data instead of generated explanation text.

The assistant is only for explanation. The pass or fail result comes from SHACL validation.

## Production Readiness

This system is suitable for demonstrating the architecture:

```text
PDF -> Document Intelligence -> OCR/Vision -> Requirement Extraction -> Canonical Rule Model -> Review -> SHACL -> Validation
```

It is not yet production-grade because DIN standards contain exceptions, cross-references, diagrams, tables, and legal wording that need stronger extraction validation. For production use, the next required steps are:

- replace CLI review flags with an actual human review decision file or UI
- add stronger benchmark evaluation for Qwen3.5 text extraction and Qwen3-VL image observations
- expand the canonical rule model for exceptions, scope, applicability, and references
- expand deterministic SHACL templates beyond the current wheelchair-route rule families
- add benchmark PDFs with expected canonical-rule gold data
